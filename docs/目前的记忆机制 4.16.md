目前项目记忆机制是一个 “统一记忆表 + chunk 切块 + 可选 ChromaDB 向量索引 + 场景权限检索” 的结构。

简单说：

日记 / 素材 / AI 对话 / 广场帖子 / 广场评论 / 社交私聊
        ↓
app.memory.ingestion 适配成统一记忆
        ↓
memory_documents 保存原文级记忆
        ↓
memory_chunks 保存切块后的片段
        ↓
如果 MEMORY_VECTOR_ENABLED=true
        ↓
调用 embedding provider 生成向量
        ↓
写入 ChromaDB
        ↓
聊天 / 分身 / 社交匹配时先查 ChromaDB，失败则 fallback 到 SQLite 关键词检索

记忆数据存在哪里
目前有两层：

第一层：SQLite / 主数据库

memory_documents

第二层：ChromaDB

路径来自：

MEMORY_DIR=./memory_store
实际 ChromaDB 大概会在：

riji-backend/memory_store/chroma
当前 collection 名会是：

riji_memory_chunks_dashscope_1024
因为你的配置是：

provider = dashscope
dimensions = 1024
如果用 hash provider，则 collection 是：

riji_memory_chunks_hash
这样做是为了避免 64 维 hash 向量和 1024 维通义向量混在同一个 Chroma collection 里。

素材什么时候进入记忆系统
这里的“素材”如果指 RawMaterial，它会在这些时机进入统一记忆：

创建素材时
在 material/service.py 里，create_material 创建素材后会调用：

from app.memory.ingestion import ingest_material
ingest_material(db, material)
所以流程是：

用户创建素材
↓
写入 raw_materials
↓
调用 ingest_material
↓
创建 memory_document(source_type="material")
↓
切成 memory_chunks
↓
如果向量开启，则写入 ChromaDB
更新素材时
update_material 更新素材字段后也会调用：

ingest_material(db, m)
这会根据：

user_id + source_type + source_id
找到原来的记忆文档，如果内容变了，会删除旧 chunks，重新生成 chunks，并重新索引向量。

素材做情绪提取后
extract_emotion 把 AI 情绪结果写回素材后，也会调用：

ingest_material(db, m)
所以情绪信息也会同步进记忆 metadata。

什么时候真正进入 ChromaDB
真正写入 ChromaDB 的时机在 memory/service.py。

所有 ingestion 最终都会调用：

create_memory_document(...)
然后它会：

chunks = chunk_text(...)
db.add(chunk_row)

from app.memory.indexer import index_chunks
index_chunks(user_id, chunk_rows)
所以准确地说：

只要 create_memory_document 成功创建/更新记忆，并且 MEMORY_VECTOR_ENABLED=true，就会立刻尝试写入 ChromaDB。
触发条件是：

MEMORY_ENABLED=true
MEMORY_VECTOR_ENABLED=true
chromadb 已安装
content 非空
embedding provider 可用
你的当前配置下，写 ChromaDB 时会做：

1. 把素材内容切 chunk
2. 调用通义千问 text-embedding-v4
3. 得到 1024 维向量
4. collection.upsert 到 ChromaDB
对应代码：

collection.upsert(
    ids=[chunk.id for chunk in chunks],
    documents=texts,
    embeddings=_embed_texts(texts),
    metadatas=[...],
)
历史素材会不会自动进入 ChromaDB
不会自动全部进入。

新产生的素材会在业务流程里自动进入记忆系统和 ChromaDB。

但已有历史数据需要手动跑脚本：

cd riji-backend
python scripts/reindex_memories.py
如果只是要重建已有 memory_chunks 到 ChromaDB：

python scripts/reindex_memories.py --rebuild-vector-index
如果两件事都要做：

python scripts/reindex_memories.py --rebuild-vector-index
这个脚本会覆盖这些来源：

diary
material
chat_session
plaza_post
plaza_comment
social_message
相关脚本在 reindex_memories.py。

检索时怎么用这些记忆
检索入口在 retriever.py。

流程是：

如果 MEMORY_VECTOR_ENABLED=true
    先查 ChromaDB
    根据场景过滤 visibility
    如果查到结果，返回向量结果

如果 ChromaDB 不可用 / 没结果 / 报错
    fallback 到 SQLite 关键词检索
也就是说，ChromaDB 是优先路径，但不是唯一路径。

场景权限由 permissions.py 控制，大概是：

chat：可以用 private、avatar_only 等用户自己的记忆
avatar_comment：可以用适合分身表达的记忆
agent_to_agent：不能用 private，只能用 public / school / match_card 等可共享信息
这样是为了避免日记、私聊、AI 对话这种私密内容被分身拿去公开社交。

当前最需要注意的两个问题
第一，你现在 .env 里 API key 是占位值：

DASHSCOPE_API_KEY=your-dashscope-api-key
所以如果你希望素材真的进入 ChromaDB，并使用通义千问向量，需要改成真实 key：

DASHSCOPE_API_KEY=sk-你的真实key
然后重启后端。

第二，目前 create_memory_document 里对 ChromaDB 写入异常是静默吞掉的：

try:
    index_chunks(user_id, chunk_rows)
except Exception:
    pass
所以如果 API key 错了、网络失败、DashScope 报错，业务不会挂，但你也不容易发现 ChromaDB 没写成功。

这个地方我建议后续加一行 warning 日志，或者在 memory API 里加一个“向量索引健康检查”接口。

一句话总结
目前你的记忆机制是：

所有素材先进入 memory_documents / memory_chunks 作为可靠的长期记忆底账；
如果开启 MEMORY_VECTOR_ENABLED，则在创建/更新记忆时同步写入 ChromaDB；
聊天、分身、社交匹配时优先用 ChromaDB 语义检索，失败再退回 SQLite 关键词检索。
而“素材什么时候进入 ChromaDB”的答案是：

素材创建、更新、情绪提取后，会调用 ingest_material；
ingest_material 创建/更新 memory_document 和 memory_chunks；
只要 MEMORY_VECTOR_ENABLED=true 且 embedding API 正常，就会立刻调用 index_chunks 写入 ChromaDB。
